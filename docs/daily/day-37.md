## 적용 범위

이 문서는 38~41일차 데이터 모델·규칙·유형별 화면 구현의 기준이다. **현재 저장된 모든 워크스페이스는 업무용**이며 `type` 필드가 아직 없다. 아래 모임용 정책은 구현 목표이고, 37일차에 모임 공간·투표·개인 통합 캘린더가 동작한다고 뜻하지 않는다. 기존 공간의 유형을 임의로 바꾸거나 기존 데이터를 재작성하지 않는다.

## 유형과 역할

| 항목 | 업무용 `work` | 모임용 `meetup` |
| --- | --- | --- |
| 생성 | 로그인한 이메일 계정이 유형과 이름을 선택해 생성. 생성자는 장(`owner`) | 동일. 유형 변경은 초기 버전에서 제공하지 않음 |
| 초대 | 장만 이메일 초대 링크를 생성·철회·현황 조회. 초대받은 이메일로 로그인한 뒤 만료 전 수락 | 동일. 모임 제안 참여와 공간 가입은 별개의 권한 |
| 공통 화면 | 채널·DM 채팅, 업무 보드, 팀 캘린더, 업무 현황 홈 | 채널·DM 채팅, 모임 제안·투표, 모임 캘린더, 다음 약속·미응답 홈. 업무 보드 숨김 |
| 장 | 초대·멤버 관리 및 일반 멤버의 대화·업무·일정 권한 | 초대·멤버 관리 및 일반 멤버의 대화·제안 권한. 제안 확정 정책을 우회하지 않음 |
| 멤버 | 참여 중인 공간의 채널·팀 업무·팀 일정 조회, DM은 본인 참여 방만 조회 | 참여 중인 공간의 채널 조회, DM은 본인 참여 방만 조회. 제안·확정 일정의 상세는 해당 참석 대상에게만 표시 |
| 비회원 | 공간·채널·DM·업무·일정 접근 불가 | 동일. 향후 외부 투표 링크는 해당 제안의 제한된 열람·응답만 허용하며 공간 가입 권한을 주지 않음 |

**공통 원칙:** 로그인만으로 공간 권한이 생기지 않는다. 서버는 매 요청의 현재 멤버십을 확인하고, Firestore Rules도 읽기 대상을 제한한다. 사이드바의 장 전용 메뉴 숨김은 안내이며 서버 권한 검사를 대신하지 않는다. 공간 간 데이터는 합쳐서 조회하지 않는다.

## 일정·대화 공개 범위

| 데이터·행동 | 읽기 | 쓰기·변경 |
| --- | --- | --- |
| 업무용 채널 메시지 | 해당 공간 멤버 | 서버가 현재 멤버십 확인 |
| DM 메시지·원문 링크 | 해당 DM 참여자이며 현재 공간 멤버 | 서버가 두 조건 확인. 원문 링크도 동일 |
| 업무 제목·요청자·담당자·마감·상태, 기존 팀 회의 | 해당 업무 공간의 모든 멤버. DM에서 만든 업무도 **업무 정보만** 공개 | 업무 생성은 멤버, 업무 상태 전이는 담당자·요청자별로 서버 검증. 기존 팀 회의 등록은 멤버 |
| 모임 제안·투표·확정 일정 상세 | 해당 모임 공간의 참석 대상과 제안자. 초대 전 비회원은 제외 | 멤버가 제안, 참석 대상만 본인 응답. 제안자만 수정·취소, 장의 관리 개입은 별도 감사 기록이 준비된 뒤 허용 |
| 개인 통합 캘린더 | 로그인한 본인의 권한 있는 업무 일정과 본인이 참석 대상인 모임 일정 | 원본 공간에 기록. 다른 공간에 제목·참석자·장소·DM 원문을 복제하지 않음 |
| 다른 공간에 공유할 가용성 | 사용자가 명시적으로 동의한 시간대의 `busy/free`만 | 본인이 범위·만료를 설정·철회. 기본값은 공유 안 함 |

모임 일정은 **제안 → 참석 대상 응답 → 전원 찬성 시 서버 트랜잭션으로 한 번만 확정**한다. 생성자 자동 찬성은 기본 정책으로 채택하되 화면에서 명시한다. 불참·변경 요청·미응답은 찬성이 아니다. 참석 대상·날짜·시간·장소 변경 시 버전을 올리고 이전 응답을 무효화한다. 응답 기한이 지나도 자동 확정하지 않는다. 반복 일정은 승인된 규칙과 개별 회차를 구분하며 무한 선생성하지 않는다. 이 전이는 49~61일차에 구현·검증한다.

## 기존 업무 정책과 현재 구현

- 업무 생성: 선택한 메시지의 **한 건**을 제목 초안으로 쓰고 담당자·마감·설명·예상 시간·검수는 직접 정한다. 현재 `suggestTask`는 최대 8개 메시지를 AI에 보내므로 기획과 다르다. 47일차에 단일 메시지·규칙 기반 제목으로 바꾼다.
- 요청 즉시 업무 정보는 팀에 공개하고 원본 DM은 참여자에게만 공개한다. 본인을 담당자로 지정해 생성하면 즉시 `ACCEPTED`, 다른 담당자면 `REQUESTED`다. 담당자 수락 전 일정은 미확정으로 표시한다.
- 담당자만 수락·거절·진행·마감 변경 제안·검수 제출을, 요청자만 제안 승인·거절과 검수 승인·반려를 한다. 서버는 현재 멤버십과 상태를 함께 확인한다. 제안 승인 전 기존 마감은 유지된다.
- 현재 검수 기간 입력은 1~10근무일이며 기획 기준은 **1·2·3근무일**이다. 기존 업무 기록은 보존하고 새 요청 UI·서버 범위를 업무 정책 정비 단계에서 맞춘다. 근무시간·공휴일 계산도 기존 동작을 회귀 검증한다.
- 팀 캘린더에는 업무 기간·검수 기한·회의가 보이며 팀 전체/내 담당/내 검수 필터가 있다. 업무량 충돌 경고는 미구현이다. 모임의 제안 투표와 기존 팀 회의를 같은 데이터로 취급하지 않는다.

## 서버·화면 검증 경로

| 상황 | 서버·Rules 결과 | 화면 및 재시도 |
| --- | --- | --- |
| 장이 초대 생성·조회·철회 | `ownerId`와 현재 `members/{uid}.role=owner`를 모두 확인. 소유자 문서만 남고 멤버십이 사라져도 거부 | 관리 화면에 오류 표시. 초대 현황은 새로고침 버튼으로 재조회 |
| 일반 멤버·비회원의 초대 관리 | `permission-denied`. 초대 토큰 원본은 클라이언트 직접 읽기 불가 | 멤버에게 관리 메뉴 미표시. 권한 오류는 명확한 메시지로 표시 |
| 공간 목록 구독 실패 | Firestore 오류. 기존 목록이 있어도 현재 권한으로 간주하지 않음 | 빈 공간으로 오인해 생성을 유도하지 않고 오류 화면과 **다시 시도** 제공. 계정 전환 가능 |
| 초대 링크 만료·철회·이메일 불일치 | `deadline-exceeded`·`failed-precondition`·`permission-denied` | 링크 상태 안내, 같은 이메일 로그인 또는 새 초대 요청. 수락을 자동 반복하지 않음 |
| 공간 멤버십 철회 | 채널·업무·팀 회의 읽기 거부. DM은 멤버십과 참여자 조건 모두 필요 | 구독 실패 안내. 접근 권한이 복구된 뒤 수동 재연결·새로고침 |
| 업무 상태 경합·권한 변경 | Functions에서 현재 멤버십·담당자/요청자·상태 확인. `failed-precondition` 또는 `permission-denied` | 최신 목록을 확인하고 유효한 동작만 다시 시도. 중복 요청을 자동 재전송하지 않음 |
| 회의·일정 조회 실패 | 현재 업무용 회의는 공간 멤버에게만 허용 | 캘린더 오류 표시. 연결·로그인 상태 확인 후 화면 재진입으로 구독 재시작 |

## 검증 기록

- `functions/src/index.ts`: 초대 생성·목록·철회에서 소유자 ID와 실제 `owner` 멤버십을 함께 확인하도록 보강했다.
- `WorkspaceGate.tsx`: 공간 목록 구독 실패를 빈 목록과 분리하고 다시 시도 경로를 추가했다.
- 에뮬레이터 `test:workspace`: 장·멤버·비회원의 초대/DM/채널/업무/회의 읽기, 초대 만료·철회·동시 수락, 멤버십 철회 후 접근 차단을 검증한다. 장 멤버십만 제거한 뒤 초대 관리 3개 호출 거부도 검증한다.
- 기존 업무 상태 전이·회의 생성의 회귀 범위는 `test:task-model`, `test:meeting`으로 확인했다.

## 후속 결정과 미확정 항목

- **확정한 기본값:** 유형 생성 시 선택, 기존 공간은 `work`로 해석, 장만 초대, 업무는 팀 공개·DM 원문 비공개, 모임 상세는 참석 대상 한정, 전원 찬성·생성자 자동 찬성, 타 공간 가용성 공유는 옵트인. 38일차 스키마와 41일차 UI는 이 기준을 따른다.
- **출시 전 확인:** 외부 투표 링크의 비회원 본인 확인·중복 응답 방지 수준, 실제 초대 메일 SMTP 설정과 운영 수신, 장의 제안 관리 개입·감사 방식, 개인 가용성의 만료·철회 UX, 지도·교통 API 이용 조건. 미확정 항목을 임의로 권한 확대하거나 자동 확정하는 근거로 쓰지 않는다.
