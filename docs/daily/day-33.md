## 검증 결과

- 채팅·업무 보드·캘린더의 `tasks` 구독을 `useWorkspaceTasks` 한 곳으로 모았다. 화면을 바꿀 때 같은 목록을 다시 구독하지 않고, 워크스페이스·사용자 변경 시에는 해당 범위의 새 구독을 사용한다. 구독 실패와 로딩 상태도 세 화면에 전달한다.
- 채팅의 메시지별 연결 업무를 `sourceMessageId` 기준으로 한 번 인덱싱해 메시지마다 전체 업무 배열을 반복 검색하지 않는다.
- 캘린더를 지연 로딩으로 분리하고 로딩 안내를 표시한다. 동일한 `npm run build:web` 출력 기준 초기 JavaScript가 1,182.59 kB(압축 325.26 kB)에서 916.28 kB(압축 247.67 kB)로 줄었다. 캘린더 코드 267.01 kB(압축 77.61 kB)는 캘린더를 열 때 받는다.
- 업무 카드와 원본 메시지로 이동할 때 대상 요소에 키보드 포커스를 옮기고 시각적 강조를 유지한다.
- 별도 포트의 Auth·Firestore 에뮬레이터에서 Chrome 320px·390px 채팅/보드/캘린더 가로 넘침, 320px 업무 모달 표시·Escape 닫기, 업무↔원본 이동 포커스, DM 비참여자 차단을 확인했다.
- Auth·Firestore·Functions 에뮬레이터의 캘린더 브라우저 테스트에서 필터·회의·마감 변경 제안/승인/거절을 확인했다. 여러 날짜에 걸친 검수 일정이 복수 요소로 표시되는 현재 UI에 맞춰 테스트 선택자를 수정했다.

## 구현 메모
- 변경한 파일: `useWorkspaceTasks.ts`, `App.tsx`와 스타일, 채팅·보드·캘린더 화면, `verify-task-links.mjs`, `verify-calendar-browser.mjs`, README.
- 의사결정 및 이유: 업무 목록은 세 화면에서 동일한 워크스페이스 공개 데이터이므로 상위에서 한 번 구독한다. 권한별 표시와 화면별 필터는 각 화면에 유지한다.
- 발견한 문제/해결: 기존 캘린더 브라우저 테스트가 여러 날짜에 걸친 검수 일정에 대해 단일 요소를 가정했다. 첫 일정 블록을 선택하도록 수정했다. 기본 에뮬레이터 포트가 사용 중이어서 실행 중인 개발 환경을 유지하고 별도 포트에서 검증했다.
- 다음 일차에 넘길 사항: 34일차 배포 후 실제 프로젝트의 규칙·Functions·소켓 접속과 모바일 화면을 확인할 것.

## 포트폴리오 기록
- 문제 정의: 화면 전환마다 업무 목록 구독이 다시 시작되고, 원본 이동 후 키보드 포커스가 사라져 맥락을 잃을 수 있었다.
- 선택한 접근과 대안: 워크스페이스 범위의 업무 구독을 공유하고 대상 요소에 `tabIndex=-1`을 적용해 이동 시 포커스를 지정했다. 화면 크기는 기존 반응형 배치를 유지하되 작은 뷰포트에서 실제 넘침을 검사했다.
- 검증 근거(수치 임의 생성 금지): 웹 타입 검사·린트·빌드와 위 두 브라우저 시나리오의 성공 결과. 초기 번들 크기는 Vite 빌드 출력값이며 네트워크 체감 속도나 실제 Firestore 읽기 절감량으로 해석하지 않는다.
